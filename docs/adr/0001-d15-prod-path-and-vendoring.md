# ADR 0001: D15 prod path in contract v10, semver tags, stubs and vendoring from one install command

**Status:** draft, built overnight, pending owner approval
**Date:** 2026-10-28
**Spec:** [docs/specs/shared-ci-v10.md](../specs/shared-ci-v10.md)

## Context

- **D15** (HQ decisions): branch push deploys dev, merge to `main` auto-deploys staging, prod promotes the same
  build artifact after one approval. Owner answer for this item: the approval is a GitHub **environment
  protection rule (required reviewers) on `prod`**.
- **D4/D9**: repositories in `upmatch-io`, `Store-AI-Group-Inc` and `delinecor` must not reference
  `emergy-cloud/workflows`; they get vendored, version-stamped copies refreshed by the command that bumps pins.
- **Today**: contract v9 (tag `v9`, zero adopters) maps a push to `main` straight to **prod** with no gate and a
  pull request to staging. The inline v7 copies most repositories run map a pull request to staging and a merged
  GitHub pull request to prod, and ignore pushes to `main`, so a Forgejo merge (delivered by the push mirror as a
  plain push) deploys nothing. Only one tag exists (`v9`, moving). The stubs are generated by www.emergy.cloud.
  Commit d372cff once replaced the logic files with stubs calling themselves; nothing caught it.
- **Constraints**: the platform parses `Deploy <env> from sha <sha>` and the `Deploy <env> @ <sha>` run name,
  dispatches `deploy_all`, `deploy_environments`, `environment`, `sha` and `confirm`, and matches the four file
  names; the platform's free tier gives projects `dev,prod` only (staging is optional); most private repositories
  may not be able to use required reviewers (plan dependent, see Consequences).

## Decision

We will ship **contract v10** as a new major: the shared logic maps push to a non-main branch to dev, push to
`main` to staging and a pull request to build-only, and after a successful staging deploy of a commit on `main`
the deploy logic dispatches Deploy `prod` for the **same sha**, whose job runs under `environment: prod` and so
waits for a required reviewer. The promotion is requested only when `prod` is enabled and the `prod` environment
has a `required_reviewers` rule (read with the job token); otherwise the run says why and skips, so prod is never
deployed by a push without an approval. Infrastructure apply and destroy run under `environment: prod` when prod
is enabled. Releases use immutable `vX.Y.Z` tags next to the moving `vX`; `v9` is frozen. The canonical stubs
live in `stubs/<stack>/` here, one bash command (`scripts/install.sh`) writes them into a repository in
**reference** or **vendored** mode, and `scripts/contract-check.sh` fails on self-calling logic files.

Refinements made while building (all recorded in the spec's open questions):

1. Repositories **without staging** (`dev,prod`): a push to `main` applies the same guard in Build and requests
   Deploy `prod` directly. Without this, most template and platform repositories would never reach prod from a
   merge.
2. The promotion is **idempotent**: no request when a Deploy `prod` run for the same sha is already queued,
   waiting, running or succeeded (manual `deploy_all`, re-runs).
3. "Built from main" is checked twice: the staging deploy ran from `refs/heads/main` **and** the GitHub compare API
   says the sha is on `main` (a platform redeploy of a feature-branch build to staging does not promote).
4. A failed promotion request does not fail the staging deploy (the platform would show staging as failed); it is
   reported as an error annotation on the run.
5. Pull request builds no longer assume an AWS role or upload (nothing deploys from them), and the Build
   concurrency group includes the event and ref, so a pull request check never cancels the push that deploys the
   same commit (v9 shared one group per sha).
6. Stub pushes are limited to branches (`branches: ["**"]`), so a tag push never deploys dev.
7. Every stub declares the permissions its logic needs (v9's infrastructure stubs relied on the repository
   default token permissions).
8. `delete-infrastructure` gains an optional `envs` input (to know whether prod is enabled); the stub passes the
   ENVS fallback as the other three do.

## Alternatives considered

| Option | Pros | Cons | Why not chosen |
|---|---|---|---|
| Approval: GitHub environment required reviewers (chosen) | Native UI, mail, audit trail; the same rule also gates manual prod deploys | Plan dependent for private repositories | Owner's answer |
| Approval: `dvk ship` from the Mac | Works on every plan | Outside GitHub, no audit on the run, Mac only | Kept as the fallback where the rule is unavailable |
| Promotion trigger: last step of the staging deploy job (chosen) | Runs only after every deploy step succeeded; no extra job or file | Staging run carries one more step | |
| Promotion trigger: Build dispatches prod with staging | Simplest | An approval could land before staging finished; violates "after a successful staging deploy" | Order not guaranteed |
| Promotion trigger: a `workflow_run` promotion workflow | Decoupled | A fifth file breaks the four-file contract; harder to vendor | Contract cost |
| Guard: check `required_reviewers` and skip otherwise (chosen) | Prod can never auto-deploy unreviewed | Repositories without the rule get no automatic prod | Safety first |
| Guard: always dispatch, trust the rule exists | Simple | An unprotected `prod` would deploy on every merge | Unsafe |
| Guard: refuse every prod deploy without the rule | Strict | Breaks manual prod deploys for unprotected repositories and platform users | Too strict |
| Vendoring: stubs calling local vendored logic copies (chosen) | Same stubs and logic as reference mode, byte-identical logic plus a header, D9 | Four more files per repository | |
| Vendoring: inline full workflows, no stubs | Fewer files | Diverges from reference mode; harder to verify against the source | Two shapes to maintain |
| Installer: bash, offline, reads git objects (chosen) | Runs in envs and on the Mac, no dependency, reproducible from a sha | Bash | |
| Installer: the platform's `/api/workflows.sh` | Exists | Online only; the platform is not the home of the stubs any more; no vendor mode | Wrong home |
| emergy.cloud stubs: sync script plus recorded `source.json` (chosen) | Reproducible, offline with `WORKFLOWS_DIR`, keeps the `?raw` imports | A manual sync step per release | |
| emergy.cloud stubs: git submodule or fetch at build time | Always fresh | Submodules are heavy; a build-time fetch is not reproducible | Complexity |

## Consequences

- **Positive:** one auditable prod path for every repository on v10; prod receives the exact artifact staging
  ran; approvals live in the GitHub UI; reference and vendored repositories run the same logic; a d372cff-style
  regression fails lint; a pinned repository can stay on `v10.0.0` while others follow `v10`.
- **Negative / accepted cost:**
  - Where required reviewers are not available or not configured, prod is not promoted automatically (the run
    warns); prod is then a manual deploy (platform, `dvk ship`, or a Deploy run that still runs under
    `environment: prod`).
  - Every successful staging deploy of a `main` commit (including a manual one) asks for a prod approval; reject
    the ones you do not want. A run waiting for approval holds the `deploy-prod` concurrency group; GitHub keeps
    one newer pending run and cancels older pending ones.
  - When prod is protected, an infrastructure apply on `main` and a destroy also wait for an approval.
  - Platform users on `dev,prod` without the rule lose "merge deploys prod" (v9 and the www.emergy.cloud v7 copy
    did that with no review); they deploy prod from the platform instead.
  - The guard is duplicated in `build.yml` (no-staging case) and `deploy.yml` (vendored files must stand alone,
    so no shared action); `contract-check.sh` pins both copies.
  - Variables set on the `prod` GitHub environment override repository variables inside prod-environment jobs.
- **Follow-ups:** items 9 and 10 (adoption, `docs/adoption.md`); the owner creates `prod` with required reviewers
  per repository; tags `v9.0.0`, `v10.0.0`, `v10`; optional platform support for protected prod environments.

## Implementation plan (short)

1. `.github/workflows/{build,deploy,update-infrastructure,delete-infrastructure}.yml`: v10 logic (event map,
   guard, promotion, `environment: prod`).
2. `stubs/astro/*.yml`: v10 stubs (marker, `@v10`, permissions, triggers).
3. `scripts/contract-check.sh`: self-call guard, stub checks, v10 strings; `tests/contract-check.test.sh` with
   `tests/fixtures/`; `lint.yml` runs actionlint on the stubs, shellcheck and both test scripts.
4. `scripts/install.sh` and `tests/install.test.sh`.
5. README (versioning, modes, install, D15 path, approval setup) and `docs/adoption.md`.
6. www.emergy.cloud: `website/scripts/sync-workflow-stubs.mjs`, synced stubs plus `source.json`,
   `WORKFLOW_CONTRACT_VERSION = 10`, tests, user guide and architecture copy.
